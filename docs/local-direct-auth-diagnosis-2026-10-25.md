# 本地无代理认证故障检查

后续“开启TUN仍不能登录”的独立检查见[TUN登录故障报告](local-tun-login-diagnosis-2026-10-25.md)：已复现登录前数据库连接超时，不能与本报告的无TUN HTTPS失败混为一谈。

2026-10-25。用户要求检查大陆网络、关闭系统代理时localhost/127.0.0.1认证不可用。用户随后明确：当前为保持Codex可用，已开启虚拟网卡/TUN。因此本次在线探测均不能认定为大陆无TUN直连验证。

## 已确认的失败环节

`src/lib/server/auth.ts` 的 `owner()` 调用 `client.auth.getUser()`，每次向远程Supabase认证服务核验用户。请求不是完全在本机完成。该方法返回 `AuthRetryableFetchError` 或status=0时，代码映射为503，项目入口显示「认证服务尚未就绪」。这一阶段尚未开始读取项目业务数据，图片缓存、标注量和待办预读不是这条错误的触发位置。

Supabase SDK的status=0表示未获得正常HTTP响应。SDK将底层异常转换为认证可重试错误；本项目日志又只允许有限的认证业务码，其他统一打印OTHER。因此这条日志不能区分DNS失败、TCP不可达、连接重置、TLS异常或超时。它也不能证明Supabase服务器真的返回了503，更不能据此判断密码错误。

官方依据：[getUser会发出认证网络请求](https://supabase.com/docs/reference/javascript/auth-getuser)。已对照当前安装的 `@supabase/auth-js/src/lib/fetch.ts`，其非HTTP响应异常被包装为status=0。

## 配置与当前在线探测

- Auth使用正常Supabase SSR客户端；没有在该链路设置系统代理地址或自动切换代理。`src/proxy.ts`是Next.js请求中间层，不是HTTP出站代理。
- 当前shell中HTTP_PROXY、HTTPS_PROXY、ALL_PROXY、NODE_USE_ENV_PROXY及NODE_OPTIONS均未设置；Windows系统代理ProxyEnable=0。
- 现有测试脚本的Direct策略只清理子进程代理变量，**不会绕过TUN、VPN或其DNS/路由**。普通npm dev也没有把远程后端变成本地服务。
- 当前OS解析将项目域名映射到198.18.0.151，Node DNS服务器为127.0.0.1；独立DNS查询返回ECONNREFUSED。结合用户明确的TUN开启状态，这些结果不用于推断关闭TUN时的DNS表现。
- 当前TUN下，原生HTTPS默认/IPv4与Node fetch请求Auth设置均返回200（后一轮约1.34秒）；无用户的Storage请求也返回200，仅用于证明当前HTTP可达，不代表已验证私有文件权限或完整业务。
- 同轮数据库探测TCP建立后，TLS协商连接关闭（约10.16秒）；未发送数据库用户名、密码或查询。这是另一个需关注的连接结果，不能用Auth可达推断整站可用，也不能把此结果归因于大陆直连。

证据目录：`docs/evidence/auth-direct/`。所有文件名带时间戳，不覆盖先前失败或成功。没有登录、修改业务数据、修改网络设置、部署或启动浏览器/E2E；没有更改现有认证判断。

## 如何捕获真正的无TUN结果

已新增独立命令，可在Codex暂时无法连接时运行。用户自行关闭TUN/其他网络代理后，在项目根目录执行：

```powershell
npm run diagnose:direct -- -TunOff
```

`-TunOff`只记录用户声明，不会代为关闭虚拟网卡或修改系统。脚本清理并恢复自身进程代理环境，读取被忽略的.env.local，仅允许原隔离项目。探测证书正常校验的Auth/Storage HTTP、OS与DNS解析及无凭据Postgres TLS，保存脱敏错误码和阶段时间，不打印密钥、Cookie、连接密码或业务正文。

结果保存在 `docs/evidence/auth-direct/probe-时间戳.json`。重新开启TUN恢复Codex后，可直接读取该本地报告，无需分享密钥。报告成功生成不代表各个服务探测成功。

## 根据结果采取的修复

| 真正无TUN的结果 | 应解决的层面 |
| --- | --- |
| 仍解析成198.18/198.19，或域名解析失败 | DNS仍被代理软件/本地解析器影响，或上游DNS不可用；先核对解析与路由，不能把延长等待当作解决 |
| 有正常公网IP，但TCP/TLS失败或超时 | 本地到云服务的链路问题；缓存和SQL优化无效，需要先验证可直连服务入口/部署链路，无法仅靠localhost或前端代码保证可达 |
| 原生HTTPS成功、Node fetch失败 | 定向检查Node的DNS地址族、TLS信任及HTTP栈；仅在证据支持时做进程级修正，不关闭证书校验 |
| Auth设置可达，但实际用户核验仍status=0 | 继续捕获实际认证请求的脱敏底层错误，检查刷新令牌请求与瞬时连接故障；设置接口成功不能替代真实登录核验 |
| Auth可用而数据库或Storage失败 | 分别处理对应域名、端口、TLS及网络路径，不将认证成功当作完整本地测试通过 |

若要求在远程Supabase本身不可达时仍能独立开发，需要另行评估真正的本地开发后端或经验证可直连的开发后端；这是架构/运行环境选择，不能伪装成已修好的网络参数，也不能通过绕过登录校验实现。本轮未实施此类调整。

## 当前结论

用户已自行关闭TUN并运行诊断，报告：[真实无TUN探测](evidence/auth-direct/probe-1792917819229.json)。用户声明TunOff=true，未观察到Fake-IP，进程HTTP代理禁用。该样本定位到TCP之后、TLS完成之前的连接失败：

| 环节 | 实际结果 | 判断 |
| --- | --- | --- |
| OS域名解析 | 104.18.38.10、172.64.149.246，约54ms | 项目域名能获得正常公网IPv4，不能将本轮失败简单归因于完全无法解析 |
| 独立DNS查询 | DNS服务器127.0.0.1，A/AAAA查询ECONNREFUSED | 存在本地DNS查询路径异常；与OS解析结果不同，需要单列，但它不足以解释已经建连后的TLS重置 |
| 原生HTTPS默认地址族 | TCP约270ms建立，12秒超时，无TLS完成事件 | 请求尚未进入正常HTTP响应阶段 |
| 原生HTTPS强制IPv4 | TCP约264ms建立，约334ms连接重置，无TLS完成事件 | IPv4优先已试，不能将其当成现成修复 |
| Node fetch | 约10.74秒，UND_ERR_CONNECT_TIMEOUT | 与项目所用HTTP栈的连接失败一致；此错误可能涵盖TLS建立阶段，并非单凭名称证明TCP未连上 |
| Storage HTTPS | TCP约240ms建立，约304ms连接重置 | 认证之外的同域Storage请求也失败，符合共享HTTPS链路问题 |
| Postgres TLS探测 | TCP约137ms建立，12秒未完成TLS | 数据库同样存在建连后问题；尚未发送用户名/密码，不能归因于密码或SQL执行 |

**已复现关闭TUN时，到隔离Supabase入口的TLS前置连接失败；不是页面资源过多造成的认证503。** 结合相邻的TUN开启样本（Auth/Storage HTTP 200），问题明显随网络路径变化。单次探测仍不足以将重置责任确定归属于运营商、网络过滤设备、防火墙、中间软件或服务入口，更不能笼统宣称整个大陆都无法访问Supabase。

现有认证保护按设计将网络错误映射为503，未发现代码写死系统代理。修复方向应当是验证并更换可用的开发访问链路，或提供独立本地开发后端；延长超时、增加缓存、关闭TLS验证、跳过getUser，均不能证明已满足无代理测试要求。仅修改DNS也不能被宣称足以修复本轮已发生的TLS失败。

本轮未更改认证逻辑、网络设置或部署，**无代理运行尚未修复**。如果继续保留云端真实数据，应先评估经过实测可达的开发入口及Auth/Storage/PG三条链路；如果要求不依赖这些远程链路，则需另行设计与生产隔离的全本地开发运行方式，并明确它不能替代真实Supabase集成验收。
