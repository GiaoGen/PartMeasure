# PartMeasure 三阶段交互优化总体报告

日期：2026-10-22。三阶段代码已完成，原隔离环境已更新非生产preview；生产未发布。第一阶段已由用户验收通过，第二、三阶段的实际手感仍待用户确认。

**原来的慢有明确原因：东京链路的网络等待，被重复鉴权、串行SQL、重复加载、完整历史和逐张上传进一步放大。本轮主要减少“重复跑几趟”和“每次多做多少工作”，并让已有内容尽早显示。没有把Supabase数据库本身判定为计算能力不足，也没有承诺跨境网络变成本地速度。**

## 优化在哪里、为什么有效、用户会感受到什么

| 用户场景 | 原来主要卡在哪里 | 三阶段完成的优化 | 使用时的变化 |
| --- | --- | --- | --- |
| 资料区图片/文件反复加载 | 元数据缓存过短、图层各查一次、18张旧图缺缩略图；每个请求都付鉴权和数据库往返成本 | 统一资源缓存，约30秒新鲜/2分钟保留；图层每批6张；补齐旧缩略图；小缩略图服务端核权后复用 | 再次回来先看到已有资料；多张照片少抢连接，旧图可以先显示小预览。文件列表的复用提速不等于文件本体已经下载 |
| 图库进入照片编辑区 | 图库的640预览和编辑用标准图不是同一份图；重复挂载还会重新读取/解码 | 复用已下载预览过渡，标准图与属性并行；复用同版本标准图字节，保留最近一张闲置解码图 | 已有预览时先见画面，高清图就绪后替换；来回开同图减少传输/解码。首次进入仍可能需要下载标准图 |
| 右侧标注属性、资料区标注浮窗 | “标注文档→任务列表→逐字段完整详情”串行；完整历史也被一起取回 | 已知标注时一次业务事务聚合当前数据；同标注字段一起读；最新回复/补测原因与完整历史分开 | 首次点标注少等几轮；同标注多个字段一起出现。历史在展开时才读，仍能查更早记录和证据 |
| 待处理事项每点一次就转圈 | 详情挂载强制冷读，各字段各请求，A→B→A没有有效复用 | 同ID/revision统一缓存；同卡片当前详情批读；先呈现保留内容，后台校验 | 已看卡片切回来更快，未变化内容不必整块清空；输入仍受草稿/修订保护 |
| 刷新后图片又重传 | 之前缓存主要在页面内存，真正刷新会消失；离页还被当作清会话 | 新增有界IndexedDB图片字节缓存，离页与注销分开；刷新后新鲜核权再复用同hash字节 | 条件满足时不用再从Storage传整张图片；仍会等待页面、元数据和核权，并非刷新零请求 |
| 多张照片/文件上传慢 | 前一张从哈希、上传到处理全部结束，后一张才开始 | 最多两份在途，传输与上一张处理重叠；处理仍一次一份；遵守预留/频率预算 | 后一张更早开始；进度清楚区分传输100%、等待处理和真正可用；失败可继续同一预留，少重复上传 |
| 成果文件下载等很久 | 每4MiB重新走一轮Auth、限流、交付/文件权限与Storage请求；多份下载没有统一预算 | 有依据地改为8MiB分段；全局最多两路、缓冲/拼装预留256MiB，保留校验与超时/取消 | 较大文件少付重复请求成本；可见传输进度，可重试/取消，同时多下也有边界 |
| 回复/补测后多个区域重新加载 | 直接写回、事件回声、父级刷新和子组件各自取数叠加 | 按实体和revision失效，同次在途读取合并；当前视图驱动字段表单；无关上传不清当前详情 | 自己刚提交的内容直接显示，对端更新只拉相关数据；后台更新不覆盖未提交输入 |
| 返回标签页、Realtime偶发不稳 | 页面恢复与连接恢复没分清；临时Auth网络错误被当登录失效 | BFCache/pageshow恢复、合并焦点校验；保留SSE与游标补偿；临时故障走重连，记录固定脱敏分类 | 返回窗口少一次整片空白；短暂网络抖动减少不必要的退出，真正无权限仍停止访问 |

可以把它理解为：原来每点一次，程序都重新去仓库跑几趟，还把旧档案一起搬来；现在常看的资料留在手边，第一次取资料也尽量一次拿齐，历史需要时再拿。刷新后保留的是图片本体，访问资格仍当场检查。

## 已有的量化证据

| 检查 | 结果 | 能说明什么 |
| --- | --- | --- |
| 第二阶段固定标注首次业务读取 | 3事务/21次SQL往返/5.48秒 → 1事务/7次/2.42秒 | 该小样本业务等待减少约56%；不含HTTP鉴权、传图与渲染，不是全站p95 |
| 旧缩略图补建 | 18张缺失 → 0张；新增36个320/640版本，共103,268字节；标准图hash未变 | 旧资料具备小预览路径，不需要改原图和标注 |
| 第三阶段同一8MiB私有PDF下载 | 4MiB分段2请求约19.03秒 → 8MiB分段1请求约9.63秒；字节完全一致 | 固定鉴权/权限/Storage往返成本显著，减少请求有效；不能据此宣称带宽翻倍 |
| 新客户端缓存复用验证 | 真实新鲜核权1次，复用880字节缩略图，图片字节GET为0 | 复用门控能工作；存储适配器模拟新客户端，实际浏览器IndexedDB/硬刷新尚待人工验收 |
| 原隔离真实上传 | 两张成功；可重试失败后同一预留完成；重复complete无重复资产 | 流水线和恢复契约仍正确；样本是小图片，不代表所有手机大照片耗时 |
| 权限与连接 | B隔离、Guest未发布图片拒绝、撤销后不读取本地Blob；最终preview正常登录/私有图/SSE初始连接通过 | 提速没有用公开桶、持久授权缓存或跳过撤销实现；不等于长期断线/全部网络已验收 |

原检查中，本机到东京单次SQL网络往返约250～400ms，数据库历史执行均值通常只有数毫秒。把21次往返缩成7次，比单纯认为“换个更快数据库”更直接。旧非生产站虽然单接口比本机快，串行层级和图片传输仍会相乘，所以两边都可能慢。

连接池维持每实例2连接、闲置10秒。减少请求后，一次图库/当前任务有界并发样本的pool等待很小，没有据此盲目扩池。没有修改系统代理；“进程不使用显式代理”也不能证明设备没有VPN/TUN，更不能代替大陆手机网络实测。

## 缓存到底保留什么

- 页面内元数据：统一缓存，同项目/资源事件精准失效；约30秒新鲜、2分钟保留，最多64项/约2MiB。过期校验不强制先清空画面，写入仍检查修订。
- 页面内图片：编码字节继续受96MiB/48项预算和闲置策略管理；最近一张闲置标准图最多额外保留20秒解码结果。
- 刷新后的图片：IndexedDB最多96MiB/48项/24小时，单张最多32MiB；按内容hash及角色/项目/身份分区复用，先新鲜核权，再读字节。存储失败降级为网络。
- 不持久保存登录凭据、授权结果或整份历史；退出/换账号清理，文件隐藏/撤销与多标签失效也处理。无法把已被用户保存的私有文件远程收回。

24小时是逻辑复用期限；过期条目在后续运行时淘汰，浏览器关闭期间不能执行定时物理删除，不能把缓存TTL理解为设备上的法证级擦除承诺。

因此，首次没看过的照片、超过32MiB的大图、缓存被淘汰/过期、浏览器限制存储、换账号或新Guest会话，仍可能需要重新传图。这是容量与权限边界，不再等同“缓存根本没有实现”。

建议只花10～15分钟试下面几个动作，不必准备专业性能统计：

1. 图库打开一张照片→返回→再打开；再切两个标注，观察画面和属性是否更快、输入是否保留。
2. 待办A→B→A，展开一次历史，确认最新补测原因和旧值/附件都在。
3. 照片完整显示后刷新页面，再进入同一照片；重点感受高清图是否少等一次传输。不要退出账号后再比较缓存命中。
4. 连续选2～3张真实照片，观察后一张是否提前传输，以及100%后的处理状态是否清楚。
5. 双端回复/补测并下载一份私有成果；其中一次使用真实大陆手机移动网络，说明是否开代理。

本轮解决的是可控的重复等待、串行工作和刷新丢字节。网络传输、首次核权、标准图处理和手机自身解码仍有实际成本；哪一步仍慢或出错，直接指出对应动作即可继续定位。
