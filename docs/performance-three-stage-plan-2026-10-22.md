# PartMeasure 交互提速方案：三阶段完成

日期：2026-10-22。依据：[10月21日检查报告](interaction-performance-audit-2026-10-21.md)。本文是待实施方案，本次只交付方案，不修改应用或部署。

后续状态（2026-10-22）：用户已确认第一阶段验收通过，并依次授权第二、三阶段。三阶段代码、必要检查及同版本非生产preview已完成，见[总体报告](interaction-performance-overall-2026-10-22.md)与[第三阶段交付](performance-stage3-2026-10-22.md)；第二、三阶段实际手感与真机结果待用户验收。上句保留写方案时的历史边界。

## 预期能得到的提升

**最明显的是重复操作更快：看过的照片、标注、待办再次打开时先呈现已有内容，减少一次点击等一整轮网络的情况。首次读取与批量上传也会减少多余步骤，但无法消除实际网络传输时间。**

| 场景 | 改完后期望看到的变化 |
| --- | --- |
| 重开已看标注/待办 | 有有效缓存、没有权限变化时，争取约0.2～0.5秒呈现内容；后台校验不遮住已载内容 |
| 图库进入编辑器 | 先用已下载预览呈现画面，标准图与属性并行准备，减少空白等待 |
| 首次打开属性 | 将“标注→任务列表→逐条详情”的串行等待收敛为一次主数据读取；图片独立并行，不再等完整历史 |
| 刷新页面 | 新鲜核权后复用设备中保存的同版本图片，减少重复传输；不承诺刷新完全零请求 |
| 多张上传 | 后一张的传输可与前一张处理重叠，减少整批逐张排队；传输完成和图片处理分别提示 |
| 对端回复/补测 | 已提交数据及时显示，一次事件尽量只更新相关对象，少出现整片区域重新加载 |

以上是实施目标，并非已测结果。不承诺整体统一快几倍或上传固定减少百分之多少；优先解决可控的重复等待，再由实际使用判断效果。

## 执行方式

- 按下面三个阶段连续推进，每阶段交付可使用的改动；普通实施细节不反复停下来询问，用户可随时反馈调整。
- **目标约80%的任务时间用于代码实现，约20%用于必要检查和简短交付说明。** 不先重做一轮全面审计，不建设复杂监控/压测平台，不追求本轮出完整p95报告。
- 沿用现有Next.js、Supabase、缓存和事件机制，保留两大工作区及现有布局。npm、无Docker，不新增付费资源、常驻Worker或系统代理依赖。
- 私有权限、账号隔离、固定照片坐标、原件及回复历史保留；客户提交即已补充，工程师要求补测的现有流程保持。
- 仅在原隔离Supabase项目 `rvysclscetfqicpnzlra` 与既有非生产测试项目内工作。部署仅列为后续实施交付，不在写方案时触发，不进入生产。

## 第一阶段：先让已看过的内容好用起来

**目的：优先解决点击标注、切换待办、图库与编辑器来回时反复等待。建议占实现工作量约30%。**

### 具体工作

1. **统一缓存与读取入口。** 图库图层、编辑器、浮窗、待办按同一实体ID和revision复用数据，修正同一标注文档使用不同cacheVersion的问题。优先扩展已有QueryCache与共享读取函数，不引入新的全局状态框架。
2. **取消普通切换时强制冷读。** 详情挂载先读缓存；已有内容继续显示，后台校验。明确重试、冲突恢复、权限变化才强制重新读取。缓存过期不等于界面必须先变空。
3. **让缓存覆盖实际操作间隔。** 元数据初始新鲜窗口约30秒、内存保留约2分钟，配合现有容量上限；焦点/前后台切换改为有界校验，保留已有画面。写入、事件和权限变化继续精准失效；过期状态不据旧数据假装已提交。
4. **图库与编辑器共享预览。** 已有缩略图立即用于过渡，标准图加载后替换；标准图元数据已知时尽早加载。预览未清晰前提示正在载入高清图；正式编辑沿用标准图尺寸、hash和坐标约束。
5. **合并刷新来源。** 完成响应和Realtime对同一revision只更新一次；后台交付/上传恢复读取降低优先级。普通切换取消无消费者的请求，共享请求仍保留其他使用者。
6. **修复页面恢复。** 对返回标签页、BFCache/pageshow及会话失效分别处理，避免pagehide清理后事件连接不恢复；退出/账号切换仍清理私有内容。

主要改动位置：`api.ts`、`query-cache.ts`、`cache-policy.ts`、`use-annotation-session.ts`、`issue-detail.tsx`、`issue-inbox.tsx`、图片展示与工作台组件。

### 最少检查与交付

- 定向检查缓存命中、事件更新、账号切换及迟到响应隔离；跑涉及文件的lint、typecheck和相关现有单测，不重复跑全项目业务脚本。
- 给用户可操作版本，以及“来回点同一照片、切两张待办、返回后继续填写”三个试用动作。
- **阶段完成应能看到：已访问内容切回来明显更快，不因后台读取丢掉当前输入。** 此阶段不承诺硬刷新仍保留图片字节。

## 第二阶段：让第一次加载少跑几趟

**目的：减少图片、右侧属性、浮窗和待办冷读的真实请求成本。建议占实现工作量约40%。**

### 具体工作

1. **聚合当前标注的主数据。** 一次有界读取返回所需标注、活动测量项、最近回复/补测原因；同标注多个字段一起获取。仍保留独立annotation/issue/response/review，只合并读取。已知标注时不必先查列表再逐条读详情。
2. **历史真正按需加载。** 当前视图只取当前状态与必要摘要；展开历史才读取分页记录。新增明确的当前视图DTO，兼容原完整详情接口，不把旧接口静默截短，也不丢历史。
3. **可见图库批量读取图层。** 每批建议最多6张图片，限制返回大小；每个文件独立核权。优先用户正在点击的图片，避免后台图层请求堵住当前操作。
4. **收紧后端固定开销。** 聚合读取只经过一轮必要Auth、限流和业务事务；保持失败记账、RLS和撤销约束。先靠合并请求提速，本轮不默认改为长期身份缓存或放宽鉴权。
5. **有依据地小幅调整连接。** 消减请求后，仅在仍有明显pool等待时，对比当前2连接与小幅增加、空闲10秒与适度延长两种配置，结合总连接预算定值；不反复调参或盲目加大并发。
6. **补齐旧缩略图。** 重新确认缺失清单（上次为18张），用一次性、有界、可重复执行的任务补建；不在列表GET中做图片转换，不修改原标准图/标注。需要的元数据更新使用原隔离项目与正式契约。
7. **精简事件后的取数。** 保留现有SSE和游标补偿，事件按文件/标注/任务revision通知统一读取层；避免组件各自再查一遍。增加简短失败分类，处理明确可复现的重连问题，不重建Realtime架构。

主要改动位置：现有读取API/DAL、`annotation-service.ts`、`issue-service.ts`、共享读取层、`project-live.tsx`及受影响组件；数据库连接设置仅按必要结果调整。优先无schema变更实现。

### 最少检查与交付

- 聚合接口保留少量关键检查：正常读取、跨项目拒绝、Guest过滤、历史仍可读；不把权限检查全交给人工。
- 复用现有分段计时，仅对一份固定测试资料做改前/改后少量请求，比较请求次数、串行轮数及主要耗时；不跑长时间压测、不拿小样本算p95。
- 阶段一的缓存结果继续保留；交付一张简短前后对照表，让用户重点试首次进入图片、点标注和切待办。
- **阶段完成应能看到：冷读的串行层级和重复请求减少，缺缩略图的旧资料可以正常显示。** 不要求本机跨境所有冷请求都低于1秒。

## 第三阶段：解决刷新重载，并整理上传、下载与最终试用

**目的：把重复打开、硬刷新和文件传输的体验连起来。建议占实现工作量约30%。**

### 具体工作

1. **实现有权限门控的图片持久缓存。** 推荐使用IndexedDB，只存按内容hash区分的不可变图片字节，不存登录凭据或授权结果。默认建议总额96MiB、最多48项、最长24小时，LRU淘汰；超预算/存储不可用时直接回退现有网络加载，不影响功能。
2. **刷新先核权，再复用字节。** 由新鲜服务端读取提供有界图片可读清单（每批最多30项，含内容版本和不透明缓存命名空间）；同角色、身份、项目与访问代次匹配后才能取本地图片。清单不能作为后续下载授权，未通过核权/离线不直接展示旧私有资料。其他私有API保持原安全边界。
3. **覆盖生命周期与失效。** 退出、账号切换清理，文件隐藏/删除、分享撤销等事件清对应内容；多标签同步失效。页面刷新不再当作退出清掉可复用字节。持久缓存优先解决图片，不默认把不断增长的回复历史存入设备。
4. **上传改为有界流水线。** 原件传输初始最多2并发，图片处理仍按当前每进程1份预算；下一张可传输，前一张在处理。先确认账号/项目预留上限，保留幂等与重试；明确区分传输/校验/图片处理/已就绪，不靠延长超时掩盖问题。
5. **减少解码和下载的多余工作。** 优先保留当前/最近一张有限解码资源，图片替换不闪空；不修改已有无损标准图。交付下载设置总体并发/内存与合理超时，少量对比现有Range成本后再调整分段，不为提速取消权限与完整性校验。
6. **提供同版本非生产入口。** 使用确定源码SHA/构建ID的非生产测试部署，核对仍为东京函数和原隔离Supabase，更新试用入口。仅在功能可用的版本上交付，避免每个小改动都重新部署。

持久化图片是相对此前“只存页面内存”的明确变化：私有图片可在设备保留最长24小时；程序清理不能承诺法证级擦除或离线远程召回。将这一项随本三阶段方案一并审阅，后续批准本方案即按这里的边界实现，不再为每个缓存参数重复询问。现阶段只写方案，不代表已经实施或获准生产发布。

### 最少检查与交付

- 必要定向检查：刷新复用同hash字节、不同账号不复用、撤销/核权失败拒绝；一组真实隔离上传成功与可重试失败，确保没有重复资产/错误ready。
- 收尾集中跑一次lint、typecheck、现有单测与build；前两阶段未改变的检查不反复执行。遵守现有限制，不自行启动浏览器/E2E，体验交由用户试用。
- 交付一个可用测试入口、简短改动清单和下面的人工试用卡；尚未完成的人体验收明确标注待验，不用自动测试替代。

## 用户人工试用卡

正常试用约10～15分钟即可给出第一轮反馈；真实大文件等待时间另计。不要求用户出专业性能报告，只需告诉我哪一步仍慢、是否有错误。

| 动作 | 主要感受/结果 |
| --- | --- |
| 图库→同一照片→返回，重复两次 | 已看内容再次打开是否更快，是否还反复空白 |
| 点同一照片上两个标注，再切回 | 属性是否尽快出现，原输入是否保留或有正常离开提示 |
| 待办A→B→A，并展开一次历史 | A是否复用，历史是否完整，旧值/补测原因是否正确 |
| 硬刷新一次，再进入同一照片 | 核权后图片是否复用，是否少等一次下载 |
| 连续上传2～3张真实照片 | 后续图片是否不再完全排队，100%后处理状态是否清楚，最终文件是否可用 |
| 工程师和客户各开一端，回复/要求补测 | 对端是否更新、未提交输入是否保留；顺便下载一份私有附件 |

其中一次在真实大陆手机移动网络试用登录/分享/上传/回复/下载即可覆盖关键外部条件；注明是否开代理，不以本机结果替代。真实注册数字OTP仍单列，不混入本次提速的完成声明。

## 控制范围与阶段收尾

本轮实施重点是用户指出的五类慢操作。先完成以上必要项，不附带迁库、Redis、新转发层、完整监控系统、长时压测、全站改版、改写历史图片或生产发布。连接根因深挖、复杂压缩策略或新存储供应商，只在三阶段后仍有明确阻塞时另列。

每阶段只留下“改了什么、必要检查结果、用户可试什么、仍有哪些限制”四项说明。人工反馈不阻止其他独立工作继续；发现明确的权限错误、历史损坏或上传错误结算则先修复。三个阶段结束，以实际可使用成果交付，体验结果由用户确认，不把检查数量当工作成果。
