# 待办整批当前详情读取方案

日期：2026-10-22。此文为用户批准的原方案；用户随后明确「开始实现」，交付及实际检查结果见[实施记录](performance-inbox-batch-2026-10-22.md)。沿用现有固定标注快照、权限及协作流程。

## 结论与上一轮的不足

可行。用户想查看的是待办位置与当前填写信息，主要是结构化JSON，可以整批准备，不需要同时下载所有照片。批量读取可以减少认证、限流预检、数据库事务和HTTP的重复往返，并不要求增加请求并发。

上一轮主要消除了图片重建，但详情预读仍偏保守：

- 仅覆盖同一资料的当前及相邻少数卡片，最多6个字段；打开浮窗时仅准备首个资料。
- 切换改变预读集合，会取消旧预读消费者并重新安排下一批。快速切换时，尚未完成的数据可能来不及准备。
- 每项填写区仍自行加载详情；共享缓存只有64项/2MiB，30秒新鲜、2分钟保留，与其他页面数据争用。简单扩大预读数量，仍可能因淘汰、失效和组件挂载而重新读取。

以上是代码中确认的限制；没有抓取用户浏览器本次请求，因此不能将其“每次点击都等待”的全部情况归结为某一个原因。

## 推荐实现

### 1. 待办摘要和当前详情一起分页返回

新增待办浮窗专用聚合读取，默认每页最多30个待办字段，并设置约1MiB未压缩JSON预算；超出按完整条目续页，不截断正文或快照。返回卡片摘要、固定标注快照、最新回复/补测原因、附件元数据、状态修订、计数和游标。

同一页复用一次请求的认证/限流预检，在同一次业务事务内完成项目核权和批量取数。复用现有表与当前详情契约；不为每个待办单独开事务或发HTTP。按本页ID集合查询，避免循环调用单项DAL。

照片元数据按文件去重，固定位置按文件/标注/修订去重。不能用当前编辑器的标注坐标替代历史固定快照。完整历史、照片字节、回复附件字节仍按需加载。

不用直接把现有6项上限改成无限大：现有读取内部还有31条SQL限制，以及其他调用方的契约，需要专用分页入口保证数量、游标和预算一致。

### 2. 一次准备整份待办，超大项目分批

打开浮窗先取首批完整当前详情；列表可立即操作，已准备的项目点击直接显示。后台自动串行续取剩余待办，不因点击另一个标注就取消整项准备任务。

初始设计边界：最多自动准备200个待办字段、应用核算的8MiB序列化内存预算；任一触顶暂停自动续取，更多项目按需续页。页数及数据预算可根据一组真实隔离样本微调，不先承诺无限项目都能一次装入内存。8MiB不是浏览器进程的硬内存上限。

常规几十项可在一批或少数几批后全部就绪；大量任务仍用同一套分页机制。不能通过自动取完所有历史和所有图片来实现“全加载”。

### 3. 浮窗统一持有详情，点击只切换选择

在浮窗层集中持有当前详情，传给现有填写区的 `currentView`。移除浮窗内各字段挂载时的独立读取；只渲染选中的填写表单和一个图片画布，不同时挂载200份表单。

已经准备的卡片不把“点击”当作重新核对接口的触发条件。专用有界工作集避免与图库共用64项缓存相互挤掉；与规范资源缓存同步修订，不能建立不受身份清理或事件失效控制的旁路缓存。

未准备完成的卡片允许前台优先补取；与后台共享同一资源的在途请求，禁止重复请求。可取消待办预读的条件是浮窗关闭、离开项目、账号变化或权限撤销，而不是普通标注切换。

### 4. 更新集中处理，保持信息正确

- 复用现有项目事件；某项被回复或要求补测，只合并该项返回的已提交变更或批量补取受影响的ID。
- 浮窗层负责订阅、补取与修订比较。不能只传 `currentView` 就停掉原填写区的订阅，导致对端修改后不更新。
- 多条临近事件合并处理，重复/旧修订不再取数；连接恢复、游标重同步、页面恢复时后台核对已加载工作集，保留合理兜底刷新。
- 正在输入的表单不被后台数据覆盖；保留切换未保存提醒、输入保留及提交时服务端修订检查。
- 权限撤销、401、账号切换等清理整份工作集并取消请求；普通TTL到期只安排受控后台更新，不让每次点击都变成阻塞读取。缓存不充当授权凭据。

## 并发与资源评估

| 情况 | 请求方式 | 并发边界 |
| --- | --- | --- |
| 首批30个字段 | 一个聚合请求 | 待办读取1路 |
| 例如60个普通大小字段 | 约两批串行；这是条数示例，超字节预算可能多页 | 通常仍1路 |
| 用户点击尚未准备的卡片 | 复用现有在途请求；否则前台补取并暂停发起下一后台页 | 极端最多前台1路+后台1路 |
| 另一端提交/补测 | 合并变更或定向批量更新 | 不为每个事件无限并发 |

上述上限针对该客户端的待办详情读取，不是整站连接数。多用户、图片、上传和SSE仍会占用资源。现有每进程数据库池max=2，因此不建议用几十个并行单项请求提速；一次较大集合查询更符合当前架构。

仍有成本：一次查询处理的行数、附件元数据、历史计数和序列化量增加；长正文多时先按字节分页。先用一组已有隔离数据核对响应大小、往返数及SQL耗时；若集合查询成为瓶颈，再定向调整按页集合查询，不先做连接池扩容或数据库迁移。

## 用户能感受到什么

等待集中到打开待办后的一次准备过程。数据就绪后，同图或跨资料切换的标注、最新补充信息与填写区直接从内存显示；跨照片的图片本身仍按现有图片缓存/网络规则处理。

首次打开、准备尚未结束、超大项目超出工作集、权限变化或重新进入新会话仍可能等待。预期重点是“准备后切换不再逐项等待”，不承诺首次加载瞬间完成或状态永远零请求。

## 实施与必要检查

建议一轮完成，约2–3小时（估算，非承诺）：聚合读取 → 浮窗统一状态和稳定后台准备 → 定向事件更新。代码与必要检查为主，不增加依赖、收费资源、代理层或生产部署。

只需定向覆盖分页/字节边界、固定快照不串项、切换不重读、后台与点击去重、对端更新/未保存输入及撤销清理；集中lint/typecheck/相关单测/build。小量隔离HTTP比较数量与大小，不做长时压测或浏览器/E2E；最终手感由用户试用同图多标注、跨资料及双方回复确认。

这是一份可行方案，不是已经完成的性能结果。实际响应体、30项取数成本与多用户承载尚未实测；不因计划并发受控就宣称服务器容量验收通过。
