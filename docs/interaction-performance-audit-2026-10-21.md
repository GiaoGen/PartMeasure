# PartMeasure 缓存、网络与交互性能检查报告

检查日期：2026-10-21（Asia/Taipei）。用户确认本机和 Vercel 测试站均慢。本轮只检查、采样、形成方案；未修改应用逻辑、系统代理、数据库结构或业务资料，未上传文件、部署或进入生产。正常测试账号登录和接口读取会产生正常会话/限流记账。

## 1. 结论

**慢是多个问题叠加，其中已证实的核心是：高延迟网络被许多数据库往返、串行接口和低复用缓存反复放大。没有证据支持“Supabase 数据库执行本身普遍需要数秒”。**

1. **本机后端到东京 Supabase 的单次往返很贵。** 本次已建立连接的 `SELECT 1` 为 250～397ms；一个小文件列表却要 9 次 SQL 调用，任务详情要 13 次。只有 880B 的缩略图首次也等了约 5 秒。
2. **应用让用户反复支付这些成本。** 普通 JSON 缓存仅 1～3 秒、最多 5 秒；详情挂载强制读取；图层与编辑器对相同标注使用不同缓存键；界面有“标注 → 关联任务 → 详情”的串行请求。
3. **现有图片缓存不能跨硬刷新。** 它只保留当前标签页内存中的 Blob URL；图片请求和响应都禁止 HTTP 缓存，离开页面还主动清内存。用户期待的“刷新后继续用已下载图片”未被实现。
4. **图库缩略图与编辑器标准图是两个资源。** 首次进入编辑器需要更清晰图片合理，但目前先等元数据、再完整取图/解码，缺少复用已有预览的过渡。相同标准图在同页短时间内重开，本应命中内存，不能把所有重开都解释成合理重新下载。
5. **测试站版本落后。** 最新可见 staging 为 10 月 19 日，早于 20 日取消 Worker 与 21 日界面改动。线上慢与本地慢不能当作同版本实验；线上仍可能受到旧上传管线影响。

优先修正缓存使用方式、串行加载、批量读取与请求排队，再优化上传图像成本和稳定性。现阶段没有依据先迁移数据库、采购 Redis/CDN、恢复 Worker 或要求用户开系统代理。

## 3. 实测：时间究竟花在哪里

### 3.1 本机与东京测试站

同一既有测试资料，通过正常密码登录，绕过前端内存缓存直接请求接口，记录收到完整响应体的耗时。

| 读取 | 本机生产构建 | 东京旧 staging | 本机 SQL 调用数/请求 |
| --- | ---: | ---: | ---: |
| 文件列表 | 3.44～4.46s | 0.51～0.96s | 9 |
| 图片标注文档 | 3.53～5.94s | 0.83～1.00s | 10 |
| 单标注关联任务列表 | 3.86～4.18s | 0.55～0.99s | 10 |
| 单任务详情与历史 | 3.64～4.54s | 0.75～1.23s | 13 |
| 项目待办列表 | 2.89～3.30s | 0.62～1.49s | 9 |
| 640 缩略图，880B | 首次 5.02s；随后 3.28s | 1.13～1.21s | 9 |
| 标准图，112B | 4.15～4.74s | 1.09～1.43s | 9 |

本机首张缩略图：Auth 332ms，SQL 累计 2803ms，签名 570ms，Storage 响应头 1303ms，总计约 5016ms。随后小图命中服务器字节缓存，已无签名/Storage 调用，**仍需约 3.28 秒**，其中 Auth 546ms、SQL 2729ms。

这说明：服务器小图缓存确实生效，但没有消除每张图的鉴权、限流、事务与数据库网络等待。小图已缓存仍慢，不是缓存完全没写，也不是 880B 传输需要数秒。

计时解释：`sql` 是驱动调用等待，含网络、数据库执行及锁等待；`pool` 是取得连接的等待；`preflight` 内含 SQL/pool，不能与它们再相加。`storage_fetch`/`app` 到响应头或流建立为止，不等于大文件完整传输。测试站未开启 Server-Timing，不能将其总时间拆成已知各阶段。

### 3.2 数据库引擎与网络是两件事

本次 native PG 建连 4.36s；热连接 `SELECT 1` 为 327.6/250.2/396.7ms。

隔离库 `pg_stat_statements` 自 10 月 16 日重置后的历史混合统计：

| SQL 类别 | 调用数 | 加权平均服务器执行时间 | 历史单次最大值 |
| --- | ---: | ---: | ---: |
| 涉及文件资产 | 4880 | 1.684ms | 315.298ms |
| 涉及任务 | 2134 | 3.304ms | 107.286ms |
| 涉及标注 | 499 | 4.916ms | 171.942ms |
| 涉及限流表 | 10449 | 33.469ms | 1836.818ms |

这些类别含不同语句/历史实验，不是某接口执行计划，也不能从均值保证每次查询都快。但与本次数秒客户端等待相比，**网络多次往返、连接排队和限流串行化应优先排查**。限流语句的历史高峰值得专项测量，不能将全部 SQL 累计时间叫作 Supabase 引擎计算慢。

当前隔离库只有 80 个项目、52 个未删除文件、50 个未删除标注、80 个任务，未看到足以凭数据规模解释普遍数秒等待的证据。当前样本不证明大规模查询已经优化完成。

### 3.3 并发会把慢继续放大

为隔离后端能力，另外对同一已热小图同时发 4 次 HTTP 请求，刻意绕过前端 singleflight。这是压力样本，不代表正常组件必定发送 4 个重复请求。

- 本机完整耗时 5.95/6.60/7.65/8.85s；取得池连接的累计等待约 1.61～4.16s。
- 东京旧测试站同样请求约 0.83～2.85s；未提供服务端分段，不能确认其内部等待占比。
- 当前 runtime 每进程池上限 **2**、空闲连接 **10 秒**退出；同一页面还有文件、任务、图层、上传恢复、交付和事件读取竞争这个池。

单纯提高图片并发会让更多请求等待两个数据库连接，可能更慢。应先减少请求和串行阶段，再在隔离环境根据连接总配额测试池大小/闲置策略。

## 5. 缓存机制：有什么，为什么体感仍不好

| 缓存层 | 当前实现 | 对体验的实际限制 |
| --- | --- | --- |
| JSON | QueryCache，64项/约2MiB；同键并发合并；默认项目数据3秒，很多列表显式1秒，硬上限5秒 | 用户浏览一眼再点，通常已过期；任务首次挂载还主动绕过；不是长期项目数据层 |
| 标注图层 | 图库以 `annotationVersion:refreshKey` 分键，5秒 | 编辑器对同一 URL 不传该版本，缓存不共享；每次事件增加 refreshKey 也产生新键 |
| 页面生命周期 | focus 清 JSON，切后台清 JSON，pagehide 清会话缓存/图片 | 返回标签页或刷新后再次承担网络成本；当前无统一 pageshow/BFCache 恢复协定，需浏览器验证 |
| 浏览器图片内存 | URL+内容hash/规格；48项；编码字节与在途预留总96MiB；空闲60秒；4传输并发 | 不跨硬刷新；缩略图与标准图不共享字节；只缓存编码内容，画布每次新建 Image 仍可能重新解码 |
| 服务端缩略图 | 每进程8MiB、64项、60秒，小于等于256KiB；先重新核权 | 只能省掉 Storage 签名/取图，不能省 Auth/数据库；多实例、冷启动不能保证命中 |
| 标准图/普通附件 | 服务器不保留大图字节；浏览器和响应 `no-store` | 每次内存未命中需签名+受控转发；没有 ETag/304 复用路径 |

证据代码：`src/components/api.ts:124,195,224`、`query-cache.ts:78`、`cache-policy.ts:28`、`annotated-thumbnail.tsx:85`、`use-annotation-session.ts:80`、`issue-detail.tsx:99,123`、`image-memory.ts:18`、`private-image-cache.ts:27`、`src/lib/server/file-response.ts:33`。

**此前缓存主要解决安全、有界内存和短时间重复请求；它并没有实现用户期待的“项目来回操作乃至刷新后仍立即呈现已载内容”。单测通过证明这些边界按设计工作，不能证明交互流畅。**

## 6. 发散检查发现的其他放大器

### 6.1 每个读取承担两套事务固定成本

通用接口先 Owner `getUser()`（每次访问 Auth 服务），再独立 preflight 限流事务，再进入业务事务。每个事务有 BEGIN、主体/超时设置、领域 SQL、COMMIT；业务读取还需要项目/文件核权。

以 Owner 文件列表/小图为例，preflight 4次 SQL + 业务5次 SQL = 9次；标注文档与关联任务列表各10次；详情13次。Guest 不调用 Owner Auth，但有全局限流和会话/链接检查，不能据此认为 Guest 自动更轻。

独立限流事务有理由：失败也计数，避免把限流行锁拖入整个业务事务。**不能直接删掉限流或机械合并事务。** 优先通过一条有界读取服务满足一个界面，减少反复经过这两套流程的次数；需要改变事务/授权语义时另做方案。

### 6.2 组件的数据获取层仍存在串行和重复

- 编辑器：annotation document → 选中标注 → 关联任务列表 → 每个 IssueDetail → 完整历史。按两轮对应样本相加，三阶段本机约 11.9/13.8s；这是阶段相加估算，不是浏览器实测总时间。标准图与右侧部分阶段可并行，但画布也要先等文档。
- 一标注多个字段时，卡片虽聚合，仍按字段挂载多份详情和读取重复的目标图片元数据/历史。业务模型应继续独立，传输可以聚合。
- 历史在 UI 中折叠，不代表请求按需：detailIssue 每次已查询最多100回复、全部相关附件和最多100审核。历史越长，传输和解析越多。
- 事件的查询标签已较精确，但组件刷新仍偏宽：任一 issue.changed 增加全局 issueRefresh；当前协作列表及其 useProjectUpdates 可能分别触发读取；同文件其他标注发生任务变化也会刷新当前协作列表。
- 上传成功可由直接完成响应、upload.changed、file.changed 多处触发文件列表读取。1秒合并窗口/在途合并有帮助，事件稍迟到仍可能重复。
- DeliverySection 在资料/编辑器使用时仍挂载，hidden 只隐藏展示，不停止其初始读取；没有已发布成果时还可能挂载交付编辑器，读取交付文件和上传恢复。非当前关注区域与图片竞争。
- 多数组件卸载只忽略迟到结果，没有取消不再需要的网络任务；会话切换会统一取消，但普通切换不一定释放在途工作。
- 真正刷新项目页还要先完成服务器的Owner核验和projectDetail，再发送工作区，客户端挂载后才取文件/待办/交付。根layout和项目页均为force-dynamic，不能期待Next自动缓存私有数据库读取；代理层getClaims与页面getUser也不是同一次核验。项目列表返回入口使用普通a链接，会离开当前文档，不能保留现有内存缓存。图库/编辑器内部的React状态切换则是另一种情况。

证据：`annotation-collaboration.tsx:39`、`issue-inbox.tsx:325`、`workspace.tsx:397,904,920`、`delivery-section.tsx:67`、`src/lib/server/issue-service.ts:140`。

### 6.3 图片准备完成前不能显示；图像处理确有额外成本

当前 privateImage 先完整读取响应体组装 Blob，然后 new Image 解码；不能像普通渐进图片那样在接收完整标准图前逐步显示。重新挂载还会将 bitmap 清空。画布动态导入也可能增加首次代码加载，但未测浏览器 bundle 下载，不能给其编造耗时。

标准图使用原分辨率、无损 WebP。当前函数的本次合成3MP高熵 JPEG：原件 2,143,231B，标准图 7,661,590B，约3.57倍；本机处理 1344ms，两份缩略图合计约116KB。此为压力样本，不代表所有金属照片，更不能推出当前库中的小测试图都膨胀。

40MP图片仅按 RGBA 解码就约160MB（约153MiB），还未算原始缓冲、Canvas/命中层、浏览器解码与多图并存。96MiB只是编码缓存预算。当前画布图片和标注在同一 Layer，平移/绘图会更新 React 状态，脏状态还进行列表查找/比较；大量标注/高DPR手机可能掉帧，**本轮未实测帧率，不把它当已证实的数秒请求根因**。

建议显示用预览派生图和标准图分层，缓存有限解码对象/按帧合并视图更新；保持 canonical hash、宽高、归一化坐标和原件不变。更改无损标准图策略影响保真/历史契约，应作为独立决策，不覆盖已有标准图。

### 6.4 旧缩略图缺失会制造“永远加载不完”

只读核对：28张未删除的 material WebP 中，10张有匹配当前 hash 的640派生物，**18张没有**。图库没有 thumbnail 元数据就不发图片请求，只显示“图片预览准备中”；等待不会自动生成缺失派生物。旧证据预览同样有此问题。

新上传通常生成320和640，不能据此推断历史图都已有缩略图。应独立有界回填，保存原标准图/标注/历史，完成后更新派生元数据和事件；不要在列表 GET 中临时转换大图。本轮未回填，未修改旧数据。

### 6.5 上传慢包含“传输”和“传输后的多轮处理”

当前本地源码路径：浏览器计算hash → 预留 → 申请grant → 原件直传/TUS → complete → 服务器签名并下载隔离原件 → 校验hash/格式 → 方向归一化/无损标准图/320/640 → 并发写入原件与派生物 → 数据库最终结算 → 本端状态/对端事件。

- hash 已在浏览器线程中计算，不是主线程直接做 SHA；这是现有正确措施。
- >6MiB 使用6MiB chunk的TUS；≤6MiB使用签名PUT。两者均需浏览器到Storage可达，网页在本机并不使上传变成本机传输。
- **本机运行 complete 时，原件还要从东京下载到开发机，再将原件及派生图上传回东京。** 本地加工位置是额外的往返/带宽成本；东京部署可减少这一部分。
- 同一批 `for ... await send(item)` 完全逐文件：前一张完成全部处理才开始下一张。每进程又仅允许一份 complete。批量等待会累加，不能直接将所有图片并发处理。
- 当前 put 已并行写独立对象，无需再提“四次上传改并行”作为尚未实现的优化；主要未做的是分阶段流水线、图像策略和就近验证。
- 45秒I/O期限、60秒处理权/路由、客户端75秒超时是失败上限，不是快速体验目标；增加超时不能解决慢。
- `Server-Timing` 未覆盖 upload 的下载完整体、图像处理、对象写入、最终结算等细分耗时；暂时不能给上传各段占比。本轮不上传用户文件或新测试文件。

历史参考：10月20日轻量上传记录的 complete 约8.4～8.9s；完整运行有失败、针对性复核通过，不能称稳定p95。线上最新构建早于此次改造，不据本地“无需Worker”推断旧线上管线已切换。

方案：先按单文件输出阶段耗时/字节量与明确状态；原件传输有界并发、图片处理保留一个预算槽，允许下一文件传输与前一文件处理重叠；每阶段均保留原幂等/主体/配额/处理令牌。测试2张、10张、失败恢复和40MP边界，再决定并发。

### 6.6 下载也可能被重复固定成本拖慢

普通附件由服务器每次核权、签名、转发，没有内容缓存。交付下载还使用4MiB顺序Range：50MiB约13个请求，每段重新核权/签名/Storage读取；各段完整留在浏览器，最后再组成Blob，多个文件同时下载没有统一内存预算。

这会增加大文件下载延迟和手机内存压力；本轮只验证小标准图读取，未实测大文件吞吐。建议单独比较现有Range与受控流式下载，在平台限制内减少分段固定开销、统一并发/内存和超时；保持私有权限、受控撤销和断点语义。不要默认改公开桶或长期签名。

## 7. 系统代理与网络要求

### 7.1 现在到底有没有代理

本次读取到：Windows 用户代理关闭，无ProxyServer/PAC；WinHTTP显示 Direct；当前进程未继承 HTTP_PROXY/HTTPS_PROXY/ALL_PROXY/Node代理开关。诊断包装器及浏览器启动策略单测通过，它们只控制自己的子进程。

**但 Supabase HTTPS 主机与PG pooler均解析到198.18.0.0/15测试保留地址。** 这是合成/fake-IP DNS链路迹象，不是正常公网地址。无法据此判断具体软件或TUN开关，更不能把“未配置HTTP代理”写成已确认大陆物理直连。native探针的TCP阶段极短，也不能当作开发机到东京真实往返只有几毫秒。

普通 `npm run dev/start` 未调用上述 Direct 包装器；将来终端代理环境变化会影响其行为。`src/proxy.ts` 是 Next.js 请求中间件，负责CSP/会话，**不是网络代理或加速服务**。

### 7.2 实际需要哪些连接

| 发起端 | 必要链路 | 影响 |
| --- | --- | --- |
| 浏览器 | 站点 HTTPS，含同源API和SSE | 页面、元数据、私有预览/下载、事件 |
| 浏览器上传 | 授权返回的 Supabase HTTPS域名；大文件 `.storage.supabase.co` TUS | 网页能打开不代表照片能上传；两个Storage域名需分别验证 |
| Next服务端 | Supabase Auth/Storage HTTPS | 每请求鉴权、文件签名、获取/写入对象 |
| Next服务端 | 东京transaction pooler 6543或已审核直连 | 业务PG事务；HTTP代理不会自动代理pg原始TCP |
| Next事件服务 | session pooler 5432或支持LISTEN的直连 | 不能使用6543事务池执行LISTEN |

手机不需要直接连接PG 5432/6543，也无需因为当前实现而开放Supabase Realtime WebSocket；当前事件走站点同源SSE。不能把“开系统HTTP代理”当作解决所有PG与Storage问题的统一要求。

下一步网络对照应在用户允许的独立诊断中，记录实际TUN/DNS状态，在同版本东京测试站和已确认无代理的大陆真实移动网络分别采样；本轮不修改系统代理、DNS、路由或自动切线路。数据库健康/可访问与Auth、Storage、SSE及大陆整站可用分别验收。

## 8. Realtime 检查

这里的“实时”实现为 **PG事务事件表+NOTIFY → Next专用session连接LISTEN → SSE → 浏览器按事件重新读接口**，不是 Supabase Realtime 客户端直接订阅业务表。

已有机制：每个工作区一条SSE、150ms合并通知、15秒心跳、240秒轮换、断开指数退避，失败时每30秒changes补偿；隐藏页停止连接，返回重连，游标断档则resync。事件服务与退役上传Worker相互独立。

本次结果：本机SSE首次请求 **503 UPDATES_UNAVAILABLE**；稍后同配置独立5432连接约2.04s成功，角色+LISTEN/UNLISTEN约0.94s成功，角色/项目/端口和两类连接密码一致。旧staging首批SSE 200，收到第一批事件字节约1.75s。**这证明不能把一次503归为固定端口或密码错误，也不能宣布稳定性已通过。**

对流畅性的影响：

- 事件只提示“有变化”，没有直接携带完整界面数据；收到提示之后仍需支付本机3～6秒API成本。
- 服务端每轮drain再次Owner getUser，再查权限和事件；跨境本机仍慢。
- 断线补偿最快按30秒间隔执行，输入虽保留，对端可能过一阵才更新；失败持续时会变得像必须刷新。
- 前端元数据失效和多个组件订阅叠加，可能使一个事件触发多轮重读；150ms合并不等于完整请求去重。
- 会话退出/撤销清缓存是必要行为；但pagehide清会话缓存后尚无明确BFCache/pageshow恢复流程，浏览器返回时连接与缓存能否一致恢复待测。
- 24 streams/进程、30次连接/身份/分钟是限制，不是负载能力证明；多次240秒轮换、跨实例扇出和撤销期间行为本轮未实测。

方案：分开记录“写入提交 → 事件到达 → 权威数据更新 → 页面显示”四个时间；按实体revision合并订阅刷新，本端已应用写响应增量后忽略同修订重复读取；保留游标追平、权限逐次核验和输入保护。先补连接失败分类及同区域稳定性数据，再决定是否调整补偿间隔或事件载荷。

## 9. 解决方案与实施顺序

以下为本轮建议，**尚未实施**，不等于迁移/部署/持久缓存政策已经获批。保持现有两个工作区、标注与协作业务模型及历史，不做全站重设计。

### A. 先修同页重复等待：收益最直接

1. 建统一的项目实体缓存：标注/任务/当前回复按实体ID与revision共享，页面选择状态从缓存读。去掉普通详情挂载的 `load(true)`；强制重读只用于明确重试/修订冲突。回到已访问卡片先显示有效快照，再校验。
2. 统一图库图层与编辑器的annotation缓存键/种子；不要为同份文档一个传cacheVersion、一个不传。将列表返回的版本作为校验线索，而非不同组件互不共享的槽位。
3. JSON有效期按数据类别调整，例如30～120秒内存保留、SSE/写响应revision驱动失效，失联或重新可见时有界校验；解除通用5秒硬上限。数据新鲜度依赖事件与补偿，不靠盲目延长TTL；退出/账号/项目能力变化继续立即隔离。
4. 一次有界读取满足“当前标注与客户补充”：当前标注、相关活动任务、当前回复/补测原因批量返回；详情历史分开分页且展开时请求。底层issue/response/review和固定快照继续独立。
5. 已有文档/授权清单时，标准图加载与右侧协作读取并行，使用已缓存640图即时占位，再替换同坐标语义的标准图；不要先白屏等待完整大图。
6. 统一协调上传完成与事件后的失效，按实体/修订去重；非当前关注区域降低请求优先级，延后未使用交付编辑器与附件列表；取消无消费者的读取，但不能误取消被其他组件共享的请求。

预期改善：减少点击后的完整网络轮次，图库→属性→待办之间有已载内容可立即呈现。尚不能据此承诺本机冷读也能小于1秒。

### B. 减少每次真实读取的固定成本和排队

1. 可见图层按有限文件ID批量读取，例如每批最多6张、每张沿用200标注上限、限制总响应大小；避免一张照片一个独立文档事务。合并的是传输，不扩大可见性。
2. 批量领域读取复用一次必要Auth与preflight；限流按请求/资源工作量有界计数，保留失败记账和恶意请求防护。不要简单把限流搬入长业务事务。
3. 图片、当前选择的交互读取优先于后台汇总；按目标环境预算测试pool=2与小幅增加、闲置10秒与30～60秒。记录等待/总连接/错误率后决定，不能无限开连接。
4. Owner只读鉴权可评估getClaims的本地验签，但须确认项目为非对称签名，并明确撤销、封禁、邮箱确认、新鲜身份要求；敏感写/分享/下载边界保持要求。不要使用未验证getSession或用户可改metadata作权限依据。
5. 先用东京测试函数到DB的分段测量确认地域收益。目前staging已经hnd1，不把“迁到东京”冒充尚未做的配置修复；本机开发仍有远程往返，不能靠同区部署消除本机所有耗时。

数据库advisor另有两项复合外键缺覆盖索引（image_derivatives、thumbnail_jobs），两项INSERT策略current_setting重复评估，以及projects UPDATE多条宽松策略。应结合执行计划与真实工作量单独处理；没有证据把它们当成当前所有慢读主因，也不能因unused_index提示直接删除历史保护相关索引。

参考：[外键索引](https://supabase.com/docs/guides/database/database-linter?lint=0001_unindexed_foreign_keys)、[RLS初始化计划](https://supabase.com/docs/guides/database/database-linter?lint=0003_auth_rls_initplan)、[多条策略](https://supabase.com/docs/guides/database/database-linter?lint=0006_multiple_permissive_policies)、[getClaims说明](https://supabase.com/docs/reference/javascript/auth-getclaims)。

### C. 单独解决硬刷新后的图片复用

**只延长现有内存TTL，解决不了刷新。** 推荐先A/B，再选择刷新策略：

- 最小方案：私有预览端点支持内容版本ETag，浏览器改为必须重新验证的私有缓存；服务端每次先核权再304。必须同时调整preview对应的proxy响应头和客户端fetch策略，其他私有JSON保持隔离。能省字节，不能省逐张核权的等待。
- 满足“刷新后尽快重现”的方案：有限的IndexedDB/CacheStorage存不可变图片字节，用服务端下发的不透明缓存命名空间区分身份/项目/访问代次。刷新先取得一次新鲜授权的有界文件清单，确认对应hash仍可读后再使用本地字节；撤销/退出/账号切换时清理，授权失败/离线时不擅自呈现旧私有资料。

持久化会使私有图片在设备上保留超过当前页面生命周期，需要明确容量、到期、清理、多标签和共享设备行为；这是与此前“仅内存缓存”不同的安全/产品选择。本轮只给方案，未写入浏览器持久存储，也未放开公开缓存或长时签名。

### D. 处理历史图、上传和大图显示

1. 对缺失缩略图的18张旧资料先只读列出计划，再有界补建，逐文件核对原hash与标注/历史不变；补建结果不能依靠刷新猜测。
2. 上传各阶段计时、传输与处理分别显示；小规模验证传输2并发/处理1并发的流水线，保留失败恢复；新代码先验证非生产同区环境。
3. 优先增加显示用预览/有限解码复用；若需改变无损标准图，再提交保真、兼容和新派生版本方案。现有canonical不覆盖。
4. 对交付Range/多下载的固定开销、总体内存和超时建立预算；不为求快移除权限或完整性检查。
