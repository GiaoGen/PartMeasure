## 1. 结论与责任

当前实现偏重业务正确性、权限和历史保护，尚未完成低延迟协作工程。现在的同步主要靠轮询，文件处理仍依赖开发电脑，读取链路存在重复远程往返；这些是要整改的实际问题。

PRD 6.4 明确要求真实大陆手机网络验证。此前使用自动继承系统代理的脚本完成多轮真实服务验证，却没有建立独立的直连性能基线，是验证安排上的失误。成功返回不能等同于大陆可用或交互流畅。

不能据此断言 Supabase 在大陆不可用，也不能断言某一项已经解释全部延迟。用户其他项目直连可用，应作为“不同项目、区域、域名、访问路径可能不同”的依据，而不是被当前测试结果否定。

## 3. 产品应该呈现的行为

1. 上传方选图立即出现本地预览和状态，上传进度持续更新；真实提交失败必须显示失败。
2. 对方自动看到获准展示的“正在上传/安全处理中”占位，安全处理完成后自动替换成缩略图。未扫描的字节不能提前提供给对方；交付草稿不能向客户泄露占位或文件名。
3. 发测量请求、提交回复、要求重测、确认结果、发布交付，均在数据库提交后自动同步到另一端。普通流程没有“刷新任务”“刷新交付”按钮。
4. 正在打开的任务也能收到状态与历史变化；远端更新不能清空正在填写的回复或覆盖本地画布草稿。提交冲突继续明确处理。
5. 离线/重连显示简洁状态，自动补齐遗漏；失败时提供具体的“重试连接/重试提交”，不是让用户猜测何时刷新页面。

## 4. 推荐的实时方案

### 4.1 保留业务 HTTP，新增统一事件流

推荐服务端授权的项目事件流，传输优先评估 SSE：本项目当前需要服务器向浏览器通知，写操作继续使用现有 HTTP，无须为“像聊天一样即时”引入聊天系统、在线光标或复杂双向协议。每个活动项目页面一条连接，多个组件共用；同浏览器多标签可进一步协调，避免各建一套轮询。

事件流只承担通知，不把普通 API、上传和下载再绕过一个新的转发服务。沿用 Owner/Guest 的 HttpOnly 会话与项目核权；浏览器不能订阅任意项目，也不能将自报 actor 当作身份。

需要先验证当前测试托管的流式支持、最长连接、缓冲、区域和计费。不能把普通短请求包装成“永久连接”就假定可靠；若需要常驻事件网关，优先与已必需的 worker 共用受控托管资源与进程监督，职责和权限分开，不直接采购或增加服务。具体承载是部署决策，本提案尚未落地。

### 4.2 数据库提交是唯一事实来源

- 业务事务同时写入最小事件/outbox，提交后再分发；不在业务提交前广播成功，不等待外部广播服务才返回成功。
- 事件包含 eventId、projectId、单调项目序号、kind、entityId、revision。项目序号随同一项目事务锁分配，保证提交顺序；不能用普通全局 sequence 推定事务提交顺序。
- 事件种类覆盖文件状态、标注已保存修订、任务/回复/审核状态、交付发布和分享撤销；排除每次鼠标移动等高频草稿动作。
- 按角色生成允许的事件内容。可携带已核权的小型 DTO，直接更新列表；复杂详情只触发对应实体的读取，不整页重载。客户不收到工程师私有草稿、目录或未发布交付信息。
- 当前操作者用 mutation 的权威响应更新缓存，不再固定“提交后读详情、再读列表、再读整个项目”。对方用事件更新；100–200ms 窗口合并同一实体的事件，避免批量上传触发请求风暴。
- 事件至少一次投递，客户端按 ID 去重、按 revision 防倒退；订阅建立与初始快照有游标边界，消除先读后订阅的漏事件窗口。
- 断线按最后游标补齐，事件保留窗口外返回需要重新同步；短期事件保留不是无限业务历史，原有业务修订/回复仍永久依既定保护策略保存。

事件唤醒和分发也必须受控。若使用 PostgreSQL LISTEN/NOTIFY，只作提交后唤醒，outbox 才是可恢复依据；LISTEN 使用支持会话状态的独立连接，不能放在 transaction pooler 的普通业务事务连接上。分发不可由每个浏览器开数据库轮询代替；多实例扇出须验证，不能只测单进程内存广播。

### 4.3 撤销和缓存不能破坏权限

建立连接时核权只是第一步。每批业务事件分发前验证当前项目/会话/分享代次；撤销提交后停止旧会话新事件、关闭其连接，重连拒绝。撤销与分发需要明确串行边界，不能只向旧客户端发送一个“请退出”事件并依赖其自觉执行。

读取、上传完成确认、审核、下载继续独立核权；实时事件不授予业务权限。撤销前已经发送/下载的数据无法收回，不作虚假承诺。

### 4.4 为什么不直接订阅 Supabase 业务表

当前 `pm` 是私有业务 schema，Owner token 保存在 HttpOnly Cookie，Guest 是自定义项目会话而非 Supabase JWT。直接把前端连到表会改变既有权限架构。

Supabase 官方 Realtime Authorization 文档还明确：频道权限在连接期间缓存，在加入频道或更新 JWT 时重算。仅更改分享记录不能假定立即停止旧订阅。因此，Supabase 私有 Broadcast 可作为传输候选，但必须先解决 Guest 凭据、最小权限、撤销和大陆 WSS 验证；不能简单使用 public channel、开放业务表或暴露服务密钥来求快。

推荐先完成与传输无关的事件/游标契约，默认采用应用会话核权的服务端流；若实测 Supabase Broadcast 能更简单且同样安全地承载，再定版传输。任何候选都不得让业务请求多走一个无必要中转。

## 5. 缓存与请求减负

| 层次 | 推荐机制 | 失效与安全边界 |
| --- | --- | --- |
| 页面数据 | 统一内存 query cache；按身份/会话、项目、筛选和 revision 分键；并发读取 singleflight；返回工作台先展示已有数据，再按事件/游标校验 | 退出、账号切换、链接撤销清理；缓存不能替代服务端核权。首次进入必须正常验证。 |
| 写操作 | 响应返回权威实体及新版本；局部更新列表和汇总；提交按钮即时反馈；保留幂等键和 CAS | 不乐观显示“已确认/已发布”来冒充数据库成功；不明确的网络结果按幂等键恢复。 |
| CSRF | 当前浏览器会话内缓存 token，并发请求合并获取 | 登录态变化/校验失效时重新获取并有界恢复；不放长期 localStorage。 |
| 图片 | worker 一次标准化管线产生小缩略图；列表只读缩略图，打开编辑器再取标准图；可见区域加载、有限预取 | EXIF/归一化坐标继续以标准图为准；缩略图与源图同版本映射，不能改变几何含义。 |
| 私有图片复用 | 按内容版本+尺寸在内存保存 Blob/ObjectURL，限制数量和字节，LRU 淘汰 | 权限失效清理、释放 ObjectURL；默认不做持久离线缓存或公共 CDN 缓存。已交付浏览器的字节本来不可远程收回。 |
| 服务端派生物 | 可在每次核权之后复用不可变缩略图/对象字节；优先评估服务器鉴权流式读，减少每次“签名再取对象”的远程步骤 | 仍是私有桶；缓存命中也必须经过最新权限判断。保留 Range/取消/重试，不把大文件完整缓冲进函数内存。 |
| 标注/任务关联 | 先消费已有 annotationSummary、annotationRef 和 annotationId 筛选；需要多文件详细标注时有界批量获取 | 不对每个提醒再查所有详情，不一次加载全部历史。 |
| Auth/数据库 | 每个请求只解析身份一次；评估非对称 JWT/JWKS 本地验证，合并重复核权/查询、缩短事务网络步骤 | 先核对签名方式、session 撤销/禁用和邮箱确认语义；不能信任裸 getSession 或长期缓存授权。失败请求限流仍须提交，可用受控 savepoint 保留限流计数。 |

不默认新增 Redis、Service Worker、大范围预加载或全站取消 no-store。先减少当前已有的重复请求，再按实测决定必要缓存。连接池大小与空闲策略按托管实例数、pooler 限额、排队数据调优，不盲目把 2 改成大数。

## 6. 图片处理与部署位置

- 将扫描/归一化 worker 从个人电脑移到靠近 Storage/数据库的受控常驻环境；保留扫描、隔离、资源上限、重试和孤儿清理。具体托管与费用属于待定部署项。
- 核实 API 实际区域，优先减少 API↔数据库↔Storage 的跨区往返。现有测试项目是东京；这不意味着当前 API 就在东京，也不能只看地图就认定某区域大陆更快。
- 普通图片与大附件采用受控队列公平调度，避免一个大文件长期堵住所有图片；并发根据扫描器/CPU/内存和带宽小幅调整。清理任务不得长期阻塞 ready 事件分发。
- 文件字节继续优先走既有隔离上传/TUS，完成确认快速入队；不新增一次经 Next 转传整个上传的路径。大文件 hash 放入受控浏览器 Worker，避免主线程等待，服务端仍重新验证。
- 缩略图初始候选边长 320/640，实际尺寸、质量和输出预算根据画布/手机对比定版。新增派生物计入配额和清理关系，不能绕开已批准存储预算。
- 对方可以先看处理状态，但只有 ready 的安全图片才可预览。无法保证“任何大小的文件都一秒扫描完成”，应把上传耗时、排队、处理、同步各自显示并测量。

## 7. 大陆直连诊断与性能门槛

后续验证默认直连。移除脚本的自动代理继承，诊断代理必须显式选择，证据记录网络模式，不能混算。不得改 Windows 全局代理；不得用关闭 TLS 校验、反复自动重试或更长超时掩盖失败。

先在测试部署加入脱敏分段计时：浏览器到应用、Auth、连接建立/池等待、SQL、Storage 签名/首字节/传输、worker 排队/扫描/归一化、提交到事件、事件到绘制。按同样样本记录冷/热、文件大小、并发、p50/p95、失败率、请求数及字节；不记录 Cookie、连接串、分享令牌、签名 URL 或用户正文。

分别确认应用域名、Auth、Storage 上传/下载、API 到 PG、事件长连接的直连情况；浏览器不直接连接 PostgreSQL。必要时拆 DNS/TCP/TLS 诊断，不能用“数据库能连”替代其他项。开发机 HTTP_PROXY 与数据库 TCP 不是同一机制；TUN/VPN/DNS 路由需另外记录。

以下是建议验收目标，尚无达成证据，需在固定样本上验证后定版：

| 指标 | 初始目标与口径 |
| --- | --- |
| 选图、点击提交的本地视觉反馈 | 100ms 内；反馈不等于已成功保存 |
| 热态普通元数据 API | p95 ≤ 1 秒；单独报告冷启动与失败率 |
| DB 提交成功到另一在线端显示状态 | p95 ≤ 1 秒；大陆目标 ≤ 2 秒，含必要的局部读取，不只测消息传输 |
| 断线恢复后的状态追平 | 链路恢复后 p95 ≤ 3 秒；先协商固定数据量和断线时长 |
| 常规 1–5MiB 图片安全处理到缩略图可见 | 无积压时，上传完成后 p95 ≤ 3 秒为试验目标；上传本身、排队和大文件另列，不纳入伪“秒传” |
| 网络回归 | 相同直连条件对比端到端时延、请求数、字节和错误率；不得只减少刷新按钮而增加后台请求或延迟 |

若当前托管域名或供应商路径在目标运营商网络上不稳定，按 PRD 提交具体部署/对象存储替代评估，分别比较访问质量、成本和迁移边界。不是直接要求用户开代理，也不是在没有证据时把全部系统迁走。

## 8. 实施顺序与退出条件

1. **直连与分段基线**：先修测试默认网络模式并计时，准确区分连不上、排队、SQL 慢和文件慢。此步不启动新基础设施，不迁移数据。
2. **无架构变化的减负**：接入已完成 DTO、消除提醒 N+1、复用 CSRF、统一缓存/去重与 mutation 响应，缩减重复读取；按计时结果合并数据库往返。保持既有核权与失败限流。
3. **事件同步**：正式事件/outbox、游标恢复、服务端核权事件流、局部更新、撤销和重连；通过后去掉正常流程手动刷新与多套固定轮询。连接故障才启用单一、可退避的补偿同步，恢复后关闭；不改成每秒全量轮询。
4. **安全图片快速路径**：常驻 worker 就近部署、小缩略图、队列调度、受控缓存；保留大图与标注原基准。
5. **双端真实验收**：正常上传、任务回复、审核、交付均无需刷新；弹窗打开也更新；输入不丢失；撤销拒绝；断网补齐无重复；批量文件不产生请求风暴。之后在大陆真实手机网络验证登录、分享、上传、回复、下载和实时连接，包含页面前后台切换。

每步在可运行里程碑集中验证，分别报告业务回归、权限回归和性能变化，不对每个小修改跑全量浏览器。当前用户禁止自行启动浏览器/E2E，执行前保持该约束。

## 9. 后端整理边界与待定事项

数据模型、权限、事务、不可变历史可保留；需要重点整理的是 catch-all 路由、重复请求、前端临时拼接、同步机制和运行拓扑。沿用 projects/files/annotations/issues/deliveries 分域逐步收敛，不大规模重写，不重建 Supabase。

本提案需定版的架构项：事件流承载及部署/费用；撤销与分发的串行协议；事件保留窗口；缩略图输出/存储预算；Auth 本地核验与严格会话失效策略。这些尚未实施，不把原有架构批准扩展为已批准任何新基础设施。

当前状态：审计和方案已完成；优化代码、迁移、部署均未执行；大陆直连根因和目标时延待实测。此前功能 PASS 不自动失效，也不因此变成性能/整个 P0 验收通过。
