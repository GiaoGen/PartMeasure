# 待处理事项：资料分组与横滑卡片 · 2026-10-21

批准依据：用户要求卡片「只保留标注编号／名称就行，状态用颜色表示」，审阅可交互示例后回复「可以就这么改」。本次仅调整待办面板及它复用的回复呈现，不进入其他阶段、不部署。

## 行为

- 保留左下角提醒入口。打开后按资料分组，每组横向滚动小圆角矩形卡片，可触摸滑动或使用左右按钮；不新增筛选。
- 每组顺序：黄色待补测、红色待补充、绿色已补充。卡片正文只有编号／名称，状态在统一图例及无障碍名称中说明；文件级问题显示问题名称，不伪造标注编号。
- 同一标注、同一固定修订的直径／孔深／圆弧等字段合为一张卡片，下方分别填写。不同修订不合并位置。任一字段待补测优先黄，仍有待填字段为红，全部补充后绿。旧确认记录仍作为已完成历史，不重新引入确认步骤。
- 点击在列表下方切换详情，不打开工程师照片编辑器，也不改变当前资料选择；再次点击当前卡片或收起按钮可折叠。切换有草稿时保留原有确认保护，多字段汇总脏状态，避免一个表单保存误清其他表单的保护。
- 图片复用现有标准图、原图归一化坐标和只读 Konva，传入当前固定修订的一个标注，支持已有缩放／平移／适应视口。非图片文件显示受控下载和文字回复，不造几何。
- 客户继续使用原数值／照片／无法测量提交、幂等和修订冲突处理；工程师查看最新结果并可要求补测。原回复和证据、角色配色历史保留，历史默认折叠。未指定的测量方式不显示，孔深使用该请求固定的深度杆方式。
- 保存后立即更新当前卡片投影；其他人更新仍通过既有项目事件与缓存失效机制到达。不新增轮询、服务、依赖或 Worker。

## 数据与性能边界

- `/issues` 原分页读取一次附带 `fileLabel`、固定快照 `annotationLabel`、`annotationNumber`，避免为每张卡片请求详情。只在最多 31 行分页结果上补充显示上下文，原项目核权、runtime 角色和 RLS 不变。
- 编号与当前图片编辑器按 `created_at,id` 排列的未删除标注一致，是当前图片序号，不承诺永久编号。名称取任务固定修订，历史目标不会因编辑当前标注而改变。
- 仅选中卡片读取相关字段详情、标准图片；不预加载全部图片。保留 30 项分页与「加载更多」，当前已加载范围内归类；不为了全量归类一次拉完所有历史。后续页出现同修订字段会合入卡片。
- 选择项会保留已加载的相关字段，列表更新不因分页边界立即丢掉正在填写的其他字段。表单按 issue ID 保持身份，状态变化不按数组序号重新挂载。
- 未修改数据库结构、权限、Auth 或 Storage 配置，无 migration。核对 Supabase changelog 与官方 RLS 文档；本次仅扩展已有服务端 SQL 的显示字段，无新平台 API。

## 人工检查（约 3 分钟）

1. 双方打开项目左下角提醒：看到资料分组，卡片只有编号／名称；同组按黄、红、绿排列。左右滑动／按钮及键盘 Tab 可浏览。
2. 点击不同照片的卡片：列表不消失，下方切换到对应标准图片；只显示相关标注，不进入照片编辑器。缩放后位置仍对齐。
3. 选有孔深等多字段的标注：一张卡片，字段分别显示；输入一个字段后切换卡片有草稿提示，提交另一字段不会清掉前者。
4. 客户提交完成后卡片变绿；工程师要求补测后变黄，原因优先、旧值为上次提交。展开历史可见原记录和工程师蓝／客户绿色身份。
5. 文件级文字问题能填写说明／附附件，无数值输入；窄屏无页面横向溢出，只有卡片行横滑。没有资料时保留原上传入口。

与批准示例差异：正式实现使用真实标准图片及原回复能力，保留仅照片／无法测量、分页、草稿保护与失败重试；无模拟提交。没有渐变；黄色仅用于补测状态，主操作沿用既有冷蓝；无 AI 装饰；仅资料行、横滑卡片、必要图片和表单，未增加套卡片布局。
